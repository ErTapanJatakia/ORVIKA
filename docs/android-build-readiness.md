# Android build readiness

## Current baseline

The repository's committed Flutter source is platform-neutral and currently has no committed `android/` directory, Gradle wrapper, Android manifest, or Android signing configuration.

## First validation milestone

The GitHub Actions workflow at `.github/workflows/android-build.yml` generates an Android platform scaffold inside the ephemeral CI workspace. It then resolves the existing Flutter dependencies, builds a release-mode APK, verifies the APK signature with Android's `apksigner`, calculates its SHA-256 digest, and uploads the APK as a short-lived workflow artifact.

The approved Android application ID is `com.orvika.app`. The validation workflow explicitly sets and verifies this ID in the generated Gradle configuration before building. The generated Android files are intentionally not committed by this validation workflow; a permanent Android scaffold is a separate release-readiness task.

## Distribution and signing boundary

The generated Flutter template uses its development/debug signing configuration for this validation build. The resulting APK is useful for build compatibility and installation testing, but it is **not a production-signed release** and must not be published to RuStore or another app store.

The permanent Android project scaffold, release keystore custody, signing rotation/recovery procedure, and Play/RuStore packaging requirements must be implemented separately. No keystore or signing secret is stored in this repository or generated by this workflow.

## Cost and privacy

- Uses GitHub-hosted runner tooling and the free Flutter/Android build toolchain.
- No paid build service, backend, telemetry, or external application service is introduced.
- The APK artifact is retained for seven days and is not a public release.
- Existing tests and analysis checks remain unchanged.
