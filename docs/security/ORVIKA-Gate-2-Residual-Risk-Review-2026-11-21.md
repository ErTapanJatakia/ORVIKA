## 2. CSP: `style-src 'unsafe-inline'`

### Observed evidence

The latest passive ZAP artifact was generated by security assurance run [44849500455](https://github.com/ErTapanJatakia/ORVIKA/actions/runs/44849500455), artifact ID `14685010645`. ZAP 2.17.0 reported one Medium / High-confidence CSP alert with four instances. The same response policy was observed for:

- `/`
- `/robots.txt`
- `/sitemap.xml`
- the root URL without a trailing slash

The policy is configured in both `functions/_middleware.js` and `vercel.json`. The web build command uses Flutter's `flutter build web --release --csp --no-web-resources-cdn`.

### Engineering assessment

The current Flutter web implementation has not yet been proven compatible with a strict nonce/hash-only style policy. Flutter's current web initialization documentation exposes a `nonce` option for inline scripts and styles created by the engine. That capability alone does not establish that every style mechanism used by this app—including any style attributes—is covered, nor does it solve nonce delivery at the hosting layer.

A nonce-based policy would require a fresh, unpredictable per-response nonce, a matching CSP response header, and consistent propagation to the relevant Flutter-created elements. The current Vercel response-header configuration is static, while the Cloudflare Pages middleware currently adds headers but does not rewrite HTML to inject a response-specific nonce. No nonce wiring is present in `web/index.html`.

### Decision

**Keep the existing directive for now; do not weaken or remove any other CSP controls.** This is an open hardening item, not a confirmed exploit. A proposed remediation must first demonstrate, in the isolated Cloudflare validation environment, all of the following:

1. A cryptographically strong per-response nonce with no reuse across responses.
2. The same nonce in the CSP header and every relevant Flutter-generated inline style element.
3. Browser compatibility for the app's runtime styling, startup, CanvasKit and accessibility flows.
4. No regression in the existing security headers or the production deployment boundary.
5. A viable equivalent policy for every supported hosting target, or a clearly documented hosting-specific policy.

A split policy using `style-src-elem` and `style-src-attr` may be evaluated, but must not be assumed safe without runtime evidence. If nonce propagation cannot be implemented consistently across hosting targets, retain the current compatibility directive and document the residual risk rather than introducing a broken or misleading policy.

References:
- [Flutter web initialization — nonce configuration](https://docs.flutter.dev/platform-integration/web/initialization)
- [MDN — Content Security Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP)

## 3. Cache-control observations

### Observed evidence

The same ZAP artifact recorded two informational cache observations:

**Re-examine Cache-control Directives** — five responses carried `Cache-Control: public, max-age=0, must-revalidate`:

- `/`
- root without trailing slash
- `/manifest.json`
- `/robots.txt`
- `/sitemap.xml`

**Storable but Non-Cacheable Content** — five responses exposed `max-age=0`:

- `/`
- root without trailing slash
- `/brand/orvika-owl-monochrome.svg`
- `/icons/apple-touch-icon.png`
- `/orvika-analytics-bootstrap.js`

The observed routes are public app-shell or static web resources. The passive scan did not identify authenticated, user-specific or private response content among these instances. The `max-age=0, must-revalidate` behavior makes a response immediately stale and requires revalidation before reuse; the `public` directive permits shared-cache storage but does not itself establish that the response is sensitive.

### Decision

**Disposition: informational / no immediate remediation justified for the observed routes.** The current conservative revalidation behavior is retained. Do not add long-lived caching or broaden cacheability merely to silence ZAP. Revisit this decision if ORVIKA introduces authenticated pages, user-specific API responses, account data, or other sensitive dynamic content; those routes must receive an explicit private/no-store policy as appropriate.

The middleware already applies `Cache-Control: no-store` to its generated 400 and 405 responses. This does not imply that every successful static response should be no-store.
