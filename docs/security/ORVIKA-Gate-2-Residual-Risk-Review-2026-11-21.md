## 2. CSP: `style-src 'unsafe-inline'`

### Observed evidence

The latest passive ZAP artifact was generated by security assurance run [44854902417](https://github.com/ErTapanJatakia/ORVIKA/actions/runs/44854902417), artifact ID `14687231183`. The previous Gate 1 evidence recorded one Medium / High-confidence CSP alert with four instances. The same response policy was observed for:

- `/`
- `/robots.txt`
- `/sitemap.xml`
- the root URL without a trailing slash

The policy is configured in both `functions/_middleware.js` and `vercel.json`. The web build command uses Flutter's `flutter build web --release --csp --no-web-resources-cdn`.

### Engineering assessment

The current Flutter web implementation has not yet been proven compatible with a strict nonce/hash-only style policy. Flutter's web initialization API exposes a `nonce` option described as applying to inline scripts and styles created by the engine. This is a useful capability, but does not establish that every style mechanism used by this app—including any style attributes—is covered, nor does it solve nonce delivery at the hosting layer.

A nonce-based policy would require a fresh, unpredictable per-response nonce, a matching CSP response header, and consistent propagation to the relevant Flutter-created elements. The current Vercel response-header configuration is static, while the Cloudflare Pages middleware currently adds headers but does not rewrite HTML to inject a response-specific nonce. No nonce wiring is present in `web/index.html`.

### Hosting feasibility findings (21 November 2026)

The hosting investigation now has a clearer split:

- **Cloudflare Pages:** Official Pages Functions documentation demonstrates calling `context.next()` to obtain the original static response and applying `HTMLRewriter` to transform that response. Cloudflare's official Workers SPA-shell example also documents per-request nonce generation and HTML rewriting for inline script elements. This establishes a credible Cloudflare-only proof-of-concept route, not a completed ORVIKA remediation.
- **Flutter integration:** Flutter's loader configuration documents `config.nonce` for inline scripts and styles created by the engine. ORVIKA currently loads the generated `flutter_bootstrap.js` as an external async script and has no custom nonce-aware bootstrap. The pinned Flutter version in the preview workflow is 3.47.9.
- **Vercel:** Official Routing Middleware documentation confirms interception, rewrites, redirects and response/header modification, but the reviewed documentation does not establish a supported mechanism to transform the body of the existing static Flutter response. Vercel Functions can generate and stream response bodies, but routing the Flutter shell and all SPA fallback paths through such a function would be a separate architecture change requiring proof and cost/latency assessment.

Therefore, a Cloudflare Pages nonce prototype alone would not demonstrate a common solution for both supported hosting targets. Any successful Cloudflare-only result must be labelled hosting-specific unless a safe Vercel equivalent is independently demonstrated.

### Decision

**Keep the existing directive for now; do not weaken or remove any other CSP controls.** This is an open hardening item, not a confirmed exploit. No runtime CSP change has been made.

A proposed remediation must first demonstrate, in the isolated Cloudflare validation environment, all of the following:

1. A cryptographically strong per-response nonce with no reuse across responses.
2. The same nonce in the CSP header and every relevant initial and Flutter-generated inline script/style element.
3. Correct Flutter loader nonce configuration and proof of whether style attributes are still required.
4. Browser compatibility for runtime styling, startup, CanvasKit and accessibility flows.
5. No regression in existing security headers or the production deployment boundary.
6. A viable equivalent policy for every supported hosting target, or an explicit hosting-specific risk decision.

A split policy using `style-src-elem` and `style-src-attr` may be evaluated, but must not be assumed safe without runtime evidence. Allowing `unsafe-inline` for style attributes may preserve compatibility but would not eliminate all inline-style allowances or necessarily clear the scanner finding. Do not use a cosmetic directive split as a claimed full remediation.

If nonce propagation cannot be implemented consistently across hosting targets, retain the current compatibility directive and document the residual risk rather than introducing a broken or misleading policy.

## 3. Cache-control observations

### Observed evidence

The previous Gate 1 ZAP artifact recorded two informational cache observations:

**Re-examine Cache-control Directives** — five responses carried `Cache-Control: public, max-age=0, must-revalidate`:

- `/`
- root without trailing slash
- `/manifest.json`
- `/robots.txt`
- `/sitemap.xml`

**Storable but Non-Cacheable Content** — five responses exposed `max-age=0`:

- `/`
- root without trailing slash
- `/brand/orvika-owl-monochrome.svg`
- `/icons/apple-touch-icon.png`
- `/orvika-analytics-bootstrap.js`

The observed routes are public app-shell or static web resources. The passive scan did not identify authenticated, user-specific or private response content among these instances. The `max-age=0, must-revalidate` behavior makes a response immediately stale and requires revalidation before reuse; the `public` directive permits shared-cache storage but does not itself establish that the response is sensitive.

### Decision

**Disposition: informational / no immediate remediation justified for the observed routes.** The current conservative revalidation behavior is retained. Do not add long-lived caching or broaden cacheability merely to silence ZAP. Revisit this decision if ORVIKA introduces authenticated pages, user-specific API responses, account data, or other sensitive dynamic content; those routes must receive an explicit private/no-store policy as appropriate.

The middleware already applies `Cache-Control: no-store` to its generated 400 and 405 responses. This does not imply that every successful static response should be no-store.
